# 文字幅キャッシュの範囲と計測

`textfit.text_width_in()`は、同じ計測条件の幅だけを最大4,096件のLRUで再利用する。
1,024文字を超える文字列は計測するが保持しない。描画・折り返し・収容の条件は変更しない。

## キーと寿命

キーには文字列、ptサイズ、weight、安全係数、測定エンジンと、解決済みの`FontFace`
（ファイルパス、face index、family、style、可変軸）を含める。実測にも同じfaceを渡す。
環境変数による書体設定の変更は新しいキーとして扱い、以前の書体の幅を再利用しない。
読み込み済みフォントのファイル自体を同じ場所で差し替える場合は、
[フォント契約](font-contract.md)に従ってプロセスを再起動する。

キャッシュはプロセス内だけに存在し、ファイルへ保存しない。上限はエントリー数と文字数であり、
Python全体のメモリ使用量を固定するものではない。

## 導入時の測定

Windows、Python 3.13、游ゴシック／Consolas、Pillow BASICで、主要5デッキ
（基本9・拡張15・通常37・lead36・過密5、計102ページ）の生成と機械検査を連続実行した。
フォントを先に読み込み、文字幅キャッシュは各回空にして3回の中央値を取った。
`tracemalloc`の計測は速度への影響を避けるため別実行とした。

| 指標 | 導入前 | 導入後 |
|---|---:|---:|
| 生成と検査の中央値 | 7.651秒 | 6.334秒 |
| 文字幅関数の呼出回数 | 37,421 | 37,421 |
| 実測回数 | 37,421 | 4,212 |
| Python割当のピーク | 10,479,911 bytes | 12,188,569 bytes |

この環境では約17%短縮し、ピーク割当の増加は約1.6 MiBだったため導入した。
これは単一環境の観測であり、常に同じ速度向上を保証しない。Python割当の値はRSSや
ネイティブライブラリ全体の使用量ではない。速度をCIの固定しきい値にはしない。
3回すべてのPPTX内部パーツのSHA-256が導入前と一致し、全デッキの機械検査も合格した。
ZIPコンテナの日時は比較から除外する。

## 再計測

導入前のコミット`23d70ec`を別の作業ディレクトリへ展開し、同じ依存・書体・環境で実行する。
その作業ディレクトリで次を実行する。

```powershell
python -m tools.quality.width_benchmark current out/width-before
python -m tools.quality.width_benchmark prototype out/width-prototype
```

導入後の作業ディレクトリでは次を実行する。

```powershell
python -m tools.quality.width_benchmark installed out/width-after
python -m tests.test_width_cache
```

各出力先の`benchmark.json`へ時間、呼出・実測回数、キャッシュ統計、メモリ、全内部パーツの
ハッシュ、診断、環境・書体識別情報を保存する。異なる書体や依存の結果を直接比較しない。
新しい書体設定・測定条件を追加するときは、キーの分離と実測値の一致をテストへ追加する。
